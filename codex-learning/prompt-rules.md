# Prompt Rules

- If 2 consecutive attempts on the same task fail, reduce scope by 50% for the next attempt rather than retrying the same scope.
- Learner priority should always target the dominant failure category from retry-failure-analysis.jsonl.
- Registry compaction must deduplicate by (title, status) key before archiving — duplicate completed tasks caused 116KB bloat in superheld (13 tasks for 4 unique titles).
- Alerts must auto-downgrade to info when the triggering metric has been resolved for >30 tasks — stale high-severity alerts mislead the self-improve pipeline.
- Self-learning audits must verify metric computation logic in source code (task_metrics.py) before "correcting" metrics.json values — 8 consecutive audits (v6-v13) introduced false corrections by assuming metrics were wrong without reading the code.
- Growth-mode candidates must use unique title suffixes (e.g. timestamp or sequence number) to avoid family-cap and zombie-guard blocking on repeated runs.
- Metrics like task_registry_total and payload_bytes are CROSS-PROJECT sums (codex-memory/tasks.json + projects/*/repo/.codex-agent/tasks.json). Never "correct" them using only one registry — always discover and sum all registries before adjusting.
- When validate-metrics.sh discovers fewer registries than the existing metrics imply (sandbox mode), skip corrections for cross-project fields (task_registry_total, shared_registry_bytes, payload_bytes) — only correct local fields.
- Reviewer must apply leniency for low-risk changes (comments, docs, tests, single-file < 20 lines) — reject only for actual bugs or broken verification, not style or coverage gaps. review_rejection at 44% of retries is the #1 first-pass success bottleneck.
- External signal tasks in pending_approval for >24h with no approver should be auto-shelved during idle periods — stale pending tasks block growth-mode eligibility and waste registry slots.
- First-pass success rate must be computed from rule-outcome-trace.jsonl (recent N entries), not just registry tasks.json — registry sample (4-7 tasks) is too small for reliable measurement. Use `trace_first_pass_success_rate` in metrics.json for decisions.
- Inventory/verify fallback tasks are the #1 compute waste source — 97+ score=0 successes across 786 tasks. Per-family caps alone are insufficient; enforce a global aggregate cap on all inventory+verify score=0 successes (max 10). When the global cap triggers, the system should enter growth-mode instead of generating more zero-value introspection tasks.
- Self-learning audits MUST NOT re-correct known sandbox-unfixable fields (local_registry_bytes, metrics_input/registry_count_mismatch in self-improve-run.json). These revert on every sandbox session. Instead of "fixing" them each run, document them as ACCEPTED DRIFT in context.md and skip them. Audit cycles that only find sandbox-drift issues should report "no actionable findings" and exit without modifications.
- Self-learning audits must track diminishing returns: if the last 3 audits found 0 new actionable issues, the next audit should focus exclusively on NEW data (recent task outcomes, new failure patterns, knowledge base gaps) rather than re-checking known stable fields. Audits that re-check resolved issues waste context and add noise to decisions.md.
- Rules_hash churn guard: if >50% of tasks in a 20-task window have unique rules_hash values, the learner is modifying rules faster than they can be measured. Freeze rule modifications for the next 20 tasks (except critical failure fixes) to accumulate measurement data. Per-rule effectiveness requires stable rulesets across 10+ tasks.
- Score=0 success rate guard: if >80% of successes in a 20-task window have score=0, treat ALL of those tasks as zero-value regardless of success status. Do not count them toward family success caps or recent_success_rate. Zero-score successes inflate health metrics while producing no value.
- Task family repetition ceiling: if a single task family (by improvement_title_key) appears 5+ times in the last 20 trace entries, hard-block that family for 48h regardless of caps. This prevents the alternating-family pattern where 2-3 families trade off slots indefinitely.
- Meta-task ratio guard: if >60% of the last 50 traced tasks are meta/self-improve/inventory/verify tasks, hard-block ALL meta task generation until the ratio drops below 40%. The system must prioritize productive work over introspection. Current ratio is 77% — the system spent 240 of 312 tasks on navel-gazing.
- Audit diminishing returns enforcement: self-learning audits that find 0 NEW actionable code bugs (not data drift, not sandbox artifacts) in 3 consecutive runs must pause for 72h. Re-checking known issues or accepted drift does NOT count as a finding. Of the last 20 audits, only v15, v20, v27, v29, v32, v33 found real code bugs — the other 14 were data-correction or re-discovery cycles.
