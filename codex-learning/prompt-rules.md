# Prompt Rules

- In `agents/planner.sh` preflight edit tasks that mention an exact file plus `line`, `Expected:`, or a quoted replacement string: read the target file before planning, and if the expected text is already present classify the task immediately as `no_change_produced`; if the anchor text is absent classify as `missing_source_file`. This would have prevented repeated `review_rejection` retries on the two comment-update tasks that were really anchor/unchanged-state checks.
- In `agents/planner.sh` reject any single step whose instruction text exceeds `450` characters or contains `4+` requirement markers (`(a)`, `(b)`, semicolon-separated clauses, or `must:` lists), and auto-split it into inspect/create/verify steps before dispatch. This directly targets the repeated `review_rejection` pattern on bash test creation tasks whose first step bundled full file scaffolding plus assertions into one oversized instruction.
- In task registration or planner pre-check, when a task says “model it on”, “following the project pattern”, or references a concrete template/test file, run `test -e` on every referenced path before approval; if any path is missing, block the task as `missing_source_file` instead of letting coder/reviewer discover it later. This addresses the repeated failures around nonexistent test/template anchors and should remove wasted retries on invalid task specs.
- In `scripts/lib.sh` or the retry-classification write path, add a remap rule: if `failure_kind=review_rejection` but reviewer/evaluator text contains `already exists`, `already reads`, `anchor missing`, `target line`, or `no matching text`, rewrite the stored category to `no_change_produced` or `missing_source_file`. The current dominant bucket is over-counting review failures and hiding deterministic planning defects.
- In `orchestrator` before starting a next step, require remaining budget to be at least `estimated_step_cost + 60s`; estimate cost as `max(90s, median(previous_step_attempt_durations))`. If not enough time remains, stop after the successful implementation step, mark verification as deferred, and do not launch another attempt. This prevents the latest 490s run from burning time into an 80%-budget abort after step 2 succeeded.
